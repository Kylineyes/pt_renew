# 探索任务的领取、研究与知识沉淀

[文档导航](README.md) · [工程逻辑探索待办](exploration-backlog.md) · [项目规范](../AGENTS.md)

探索 agent 从待办领取一个具体问题，以原文细节为起点，可以自由扩展理解本任务所需的阅读与研究方向。目标是把不确定性变成可追溯的工程知识，文档和待办一起维护。

## 领取一个事项

1. 从最新 dev 阅读[当前能力](../PROGRESS.md)、相关主题和事项的全部原文细节，核对代码、较新报告与已有证据。历史未完成项可能已被后文解决，不能只按关键词领重复工作。
2. 选择一项尚未被占用的事项，在独立分支修改其唯一状态行：`状态：研究中；负责人：代理或任务标识；分支：实际分支；会话／证据：实际会话和证据路径`。没有可用身份的字段写“尚未建立”，不编造。派发子代理时还要遵守 AGENTS 的 Pi、模型及 high 要求。
3. 协调者把领取状态同步到共享 dev 后再开展长任务；按既有分支流程提交、no-ff 合并并推送。开始前 fetch 并复核远端领取状态。并发领取冲突先解决归属，已被别人领取就另选事项或明确协作，不重复开启相同研究／现场。
4. 记录本次要回答的问题、可复用材料、前置依赖和完成条件。前置未结时可以先做不依赖它的工作；需要阻塞时将状态改成“受阻”，保留负责人、原因及可继续的方向。

待办是一份可领取的研究队列。领取不是扩大产品功能、写入原件、复用旧现场批准或绕过工具约束的授权。已经有的用户授权继续有效，具体代码、截图和现场工作遵循本次范围及项目既有规范。

## 阅读和研究可以自由扩展

无需把阅读限制在事项列出的几篇文件。可以沿源码、调用方、格式、原报告和相邻模块追踪本任务所需的上下文；必要的工具和验证也可随问题展开。不要为了遵守初始链接而忽略真正的依赖。

发现文档不详细、不恰当、过时或相互矛盾时，可以直接补充或修正与本研究有关的正文、主题和引用。写明新依据及适用边界；静态推导、受控函数实验、Qt 测试、真实产品窗口和原软件往返不能互相替代。原图、冻结文件、原始日志、失败记录保持只读；修正文档的解释不等于改写原始证据。

历史报告中准确的阶段事实仍保留。若旧“尚未完成”已由后来报告补齐，在旧段落附近注明后续结论和链接；不要把旧候选改写成当时已经通过，也不要照抄旧计划执行。新结论优先沉淀到已有合适专题，确有独立问题时再新增报告并加入[完整资料索引](reference-index.md)。

## 新的不确定性怎样入队

研究中发现新的未知，先判断是否是当前问题必须解决的前置或子问题：属于完成当前事项必需的内容，可在当前范围中扩展并补正文；不适合本次探索或可独立回答的内容，立即追加独立事项，避免只藏在会话或本机日志中。

新增事项必须包含稳定编号、待回答问题、已有结论、原文具体锚点、完成条件和必要依赖。先在相关文档写清“观察到了什么、还不知道什么”，再将该段落链接到新事项；事项反向链接到同一细节。先查现有清单，已有同义事项就补充它，不重复排队。拆分时保留关系和范围，避免循环依赖。

编号采用 EX-数字，固定且不复用，不能因删除或排序而重编号。取号时检查当前清单和 Git 历史，例如 `git log -G '### EX-' -- docs/exploration-backlog.md`。索引行仅用于导航，状态只在各事项正文维护。完成的前置事项删除时，把其它事项的依赖改为结论文档链接。

## 怎样才算完成

一个事项完成的是其具体研究问题。结论可以是明确支持范围、严格拒绝边界或有证据的“不应实现”；不要求每项都产生产品代码。但必须满足列出的完成条件。工具失败、模型不可用、缺少关键输入、一次尝试未过或根因仍不明确，只能记录阶段收获与受阻状态，不能删掉事项冒充闭环。

研究结束时，在同一交付中完成下面的文档闭环：

1. 将全部有用收获写入版本控制内的文档：结论、推导／模型、可追溯依据、适用输入与候选、验证结果、失败、排除的解释、消费者约束和剩余未知。大体积原件仍在忽略目录，但报告要让远端读者理解结论；不能只链接私有日志或会话。
2. 更新对应主题和必要的 PROGRESS／HANDOFF。若正文过长，写专题报告并让主题、原段落指向具体结论；不要把待办当研究笔记的唯一保存处。
3. 将本项所有来源文档中的“探索 EX-编号”链接替换为结论段落链接，原文未知表述同步修正。保持有意义的原文锚点，避免别人引用的细节消失。其它事项的依赖／相关链接也改指结论。
4. 删除待办中的本项正文、领取索引行及所有其它对本项的导航记录，不留“已完成”条目或完成事项归档。编号和原始过程由 Git 历史追溯。结论文档中可用普通文字注明曾对应的编号，不能再链接已删除锚点。
5. 发现尚未解决的独立未知，先追加对应事项并建立双向链接，再清除已经真正完成的旧项；不能通过删项把剩余未知丢掉。
6. 运行下述文档检查和变更对应的必要验证，复核状态后按分支规范合入并推送 dev。报告说明完成／受阻的事项、沉淀文档与新增未知。

因上下文结束或无法继续而交接时，已经领取的事项保留；写清已做、未做、证据和下一步。明确放回队列时将状态改成“待领取”并清除占用字段，把阶段收获先写入正文，不能仅因 agent 离开就删除条目。

## 双向链接和核验

事项锚点固定为 `ex-数字`；来源段落使用稳定的语义锚点，初始盘点使用 `explore-ex-数字`。链接应落到相关段落／表格行，不能只到文件首页或通用目录。每项的“原文细节”至少有一处真实细节；该锚点附近必须有指回事项的链接。可将多个原文细节归到同一问题，保留全部有价值的入口。

运行标准库检查器：

```powershell
python tools/check_exploration_docs.py
```

检查仓库 Markdown 的本地相对文件／章节链接、显式锚点重复、待办编号及索引一致、状态字段、依赖存在与无环，以及每个原文细节的双向链接。历史报告中的本机绝对路径，以及路径中包含 `.local-analysis` 的相对证据链接，只作本机证据定位，不核验存在性或证据内容；它们不随 clone 或新工作树分发，不能要求为文档检查复制现场。仓库文档、源码和非忽略目标的断链仍须失败。

完成删项后再全文搜索该编号，检查是否有遗漏的待办链接；需要保留的纯文字历史编号可以保留。新增报告同步更新主题与资料索引。文档检查不证明研究结论或产品行为，涉及实现或 GUI 时仍需对应构建、测试和实际交互。

## 本次盘点如何去重

初始清单基于 `7e8477b`：扫描了 docs 的 155 份 Markdown 和根入口，发现的“未知／未完成／后续”等文字逐项与较新专题交叉核对。43 项覆盖当前未闭环工程问题，初始事项链接到 78 篇文档的 105 个细节；同一问题在旧报告中的重复提及不另立项。
