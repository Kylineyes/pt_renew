# 原文字对象创建的 32 字符复制边界验证

日期：2026-10-25。基线 `acf22bb`（origin/dev 最新），研究分支 `Kylineyes/research-text-copy-glm`；产品保持 0.10.0。

在既有 Unicorn 2.1.4 受控环境中**实际执行了原 EXE 的文字对象创建函数 `22fe:06fc`**，对 16 个边界用例逐项核对对象内存，全部通过。核心结论：**对象内的短字符串上限是 32 字符；超过 80 字符的输入先在本地缓冲截断到 80，去掉尾部空格后再截断到 32；全空格或空串不创建对象。** 这证实了此前静态推导的对象创建限制：解释器的 80 字节读取能力确实不代表对象能保存 80 字符。**完整程序的 `runtime_verified` 仍为 `false`。**

本轮没有修改产品源码、字体资源、文件方向支持、铜层覆盖或发布包；原安装与隔离副本前后摘要一致。

## 输入与执行前提

- 原安装 `D:/project/pt_renew/pt`（99 文件）全程只读，未修改。
- 仿真输入使用既有隔离副本 `main-2/.local-analysis/verification-40/runtime/pt/PT.EXE`，SHA-256 `abc56e2e8467e608c68a0ddf0b0705e8270c5c60f83f193fa991f10293ece968`；TRAXEDIT.OVR 摘要与既有基线一致。执行前后原安装与隔离副本的文件集合及 SHA-256 均不变（`input-digest.json`）。
- 装载沿用 verification-41 的 MZ 头及重定位规则，基段 `0x1000`。**注意：`22fe:06fc` 的正确线性地址是 `0x22fe*16+0x6fc = 0x236dc`**（此前研究中“`22fe:06fc`”按段值表述，换算时不要再叠加基段）。

## 调用约定与函数结构（静态复核）

由函数体实际读写指令归纳，`22fe:06fc` 是 Pascal 远调用，`retf 0x14` 共 10 个 word 参数：

| 栈位置 | 含义 |
| --- | --- |
| `[bp+6]/[bp+8]` | 链表头单元远指针（5 字节节点头） |
| `[bp+0xa]` | 层 byte |
| `[bp+0xc]` | 笔宽 byte |
| `[bp+0xe]` | 方向 byte |
| `[bp+0x10]` | 高度 word |
| `[bp+0x12]` | y word |
| `[bp+0x14]` | x word |
| `[bp+0x16]/[bp+0x18]` | 源串远指针（Pascal 短字符串） |

执行顺序：先把源串经 `3c97:0644`（min 截断复制）复制到 88 字节本地缓冲（请求上限 `0x50`=80）；调用 `22fe:01b0` 循环删除**尾部空格**（内部用 `3c97:07db` Delete 与 `3c97:0676`/`3c97:06b7`）；长度为 0 时置假直接返回（不分配）。随后调用 `0x39f7:0226` New 请求 `0x37`=55 字节并把节点头（5 字节）计入请求；复制到对象时请求上限 `0x20`=32；写坐标/高度/方向/笔宽/层；调用 `2964:4a90` 做链节点与边界计算（内部设 `DS:d4ed=1` 走解释器边界模式，把四个边界 word 写入对象 `+6..+0xd`）；最后 `3c97:025d` 移动 5 字节到对象 `+0x32`，`0x39f7:03a7` 插入链表，返回真。

对象布局与既有文档一致：`+0/+2` 坐标、`+4` 高度、`+0xe` 笔宽、`+0xf` 层、`+0x10` 方向、`+0x11` 短字符串。调用点复核（修正版扫描，见 `call-site-scan.json`）：EXE 装入映像内无 near call 直达该函数；OVR 侧共 8 处 `lcall 22fe:06fc`（重定位段值验证），分布于块 `0x7e2b`（5 处）、`0x14be7`（1 处）、`0x3d639`（2 处），其中 `0x3d639+0x615` 位于既有文档记载的 `FS` 读取流程内。早期扫描脚本因未换算 MZ 头偏移得出“未发现调用点”，已作废；方法学修正记录在证据目录的 `scan_call_sites.py` 头部。

## 受控执行范围

**真实执行的原机器码**（原生远返回）：

| 函数 | 作用 |
| --- | --- |
| `22fe:06fc` | 对象创建主体（两级复制、字段写入、失败分支） |
| `22fe:01b0`、`3c97:07db`、`3c97:0676`、`3c97:06b7` | 尾部空格删除及 Delete 内部子过程 |
| `0x39f7:0226 → 0x39f7:013d` | **New 分配**：预置 Pascal 堆状态（`[f7f3]=1` 驱动就绪、`[f7f0]=16` 总槽、`[f7f4]=0` 空表、`[f7f6]=实验堆段`）后由原堆逻辑做增量分配 |
| `0x39f7:03a7` | 链表头插入（真实执行） |
| `3c97:0244/025d/0644/062a` | 栈检查、移动、两级复制 |
| `2964:4a90`、`2964:53a3`、`2964:39a2` | 链节点与边界计算（边界模式，不绘线） |

**实验截获（不执行原代码）仅一处**：层校验 `0x39f7:02f8` 在入口截获并模拟“无驱动”分支返回 0。原因是该函数在驱动就绪时会 `lcall 0x3a52:0xa6` 查询驱动，无法离线执行；静态上调用点 `0x76b` 对返回值无实际使用（`or al,al` 后无消费该标志的分支）。此截获在结果中显式记录（`layer_checks` 计数）。

**实验设置**：实验堆段 `0x0050`（段值 ≤0xff，保证远指针压栈时高字节不越界）；源串放在堆内、其后 16 字节哨兵；每用例重建堆状态。指令预算每调用 250,000 次，超出即失败（但见下段钩子缺失对计数的影响）；越界读写、意外中断、未正常返回、栈不平衡均立即失败。对象/源串/堆外的写入一律拒绝。

**本机 Unicorn 限制（复核后量化）**：开发过程中曾观察到 `22fe:0744..0745` 的 push+lcall 序列有时不触发代码钩子（发生在把截获点设在调用点的中间版本）。复核对最终脚本做了三项抽查：其一，`len80_exact` 用例在正常与逐条单步两种执行方式下钩子计数完全一致（均为 21601），5 次重放稳定，本轮抽查未发现钩子缺失；其二，临时移任一函数的代码范围后执行立即被拦；其三，故意把返回地址改成数据段后，返回后首条“指令”即被范围检查拦截。这些是有限故障注入下的观察：**抽查未发现逃逸，不能排除钩子漏报时存在执行范围漏检**；因此钩子缺失只应假设为可能表现为少计数，本轮以内存结果而非计数为主要判据，250,000 次指令预算对 New 入口段落不是严密上界。

## 边界用例与结果

16 例全部通过（完整数据见 `create-copy-results.json`）：

| 用例 | 输入长度 | 对象保存 | 说明 |
| --- | ---: | ---: | --- |
| 空串 | 0 | 不建对象 | New 次数 0，返回假 |
| 单字符 A | 1 | 1 | |
| 单空格 | 1 | 不建对象 | 尾部空格删除后为空 |
| `A×30+Z` | 31 | 31 | 32 上限内完整保留 |
| `A×31+Z` | 32 | 32 | 恰好 32，尾字符 Z 保留 |
| `A×32+Z` | 33 | **32** | 第 33 字符被截断，Z 丢失 |
| `A×78+Z` | 79 | 32 | |
| `A×79+Z` | 80 | 32 | |
| `A×80` | 80 | 32 | |
| `A×80+Z` | 81 | 32 | 第 81 字符在本地缓冲即被丢弃（80 截断） |
| `A×80+空格×5` | 85 | 32 | 尾空格不产生“删空”效果 |
| `A×31+空格` | 32 | 31 | 先去尾空格再截 32：31 |
| `A×32+空格` | 33 | 32 | 去尾空格后仍 32 |
| 混合字母×3+ZYW | 81 | 32 | 尾部 Y、W 丢失 |
| 全空格 | 255 | 不建对象 | |
| 字段用例 | 1 | 1 | 方向 17、笔宽 7、层 3 逐字段核对 |

每例同时检查：源串尾部 16 字节哨兵未被写入（注意：**哨兵不变只证明未写，不单独证明未读**——读取上界的真实保证来自读白名单钩子，见下节）、对象 `+0x37` 之后保持零（同样只证明未写）、坐标/高度/方向/笔宽/层字段逐项相等、链节点头已写入、New 分配次数与返回值一致。字段用例中方向 `0x11`、笔宽 7、层 3 均按传入值写入对象。

## 读写约束的真实边界

- **读取**：栈区（`0x60000..0x70000`）不装读钩子——沿用 verification-41 的决定，本机 Unicorn 栈读钩子会使远返回错误跳转；因此栈内容的读取范围不受检查。栈外全部读取按白名单检查（字形表、方向表、解释器状态区、实验堆段、边界 word、堆状态区），越界即失败。**白名单内无法定位更细的读取范围**：实验堆段整体（0x500..0x8500）均在白名单内，所以“原函数没有越界读源串”在堆段内部不可区分——复制函数读多少字节由其长度字节逻辑决定，本轮结论中的读取上界由截断结果（32/80）与白名单共同支撑，不单独依赖哨兵。
- **写入**：仅栈、实验堆段、`DS:d4ac..d4b3` 边界 word、`DS:d4ed`/`DS:d4ec` 状态字节、`DS:f7f0..f830` 堆状态区及单字节状态区放行，其余写入即失败。

## 与读取/保存链的关系及限制

- **读取上限 80 与对象上限 32 是两层（静态读取链推导的预期）**：文件读取请求上限 80（见 [PCB 文字字段路径](legacy-pcb-text-path.md)），对象创建再截断到 32。据此预期长度 33–80 的文件文字导入后对象内只剩前 32 字符——该预期基于静态读取链（FS 读取 → 变换 → 本函数），函数实验只证实了对象字段上限为 32，实际 GUI 导入与保存往返未验证。
- **未运行实际导入/保存链**：本轮执行的是受控构造的单次调用（实验直接压栈参数），FS 文件读取、OVR 装载、实际 GUI 导入与保存往返均未执行。因此 32 上限结论的适用范围是**该函数本身的行为**，不是已验证的运行结论。保存函数 `OVR 0x41cd4+0x054a` 读取对象字段输出，同样未运行。
- **未执行**：DOS 启动、FS/FT 文件读取、OVR 装载、GRAPH.DRV、真实驱动状态下的层校验（`[f7f3]≠0` 的原行为）、屏幕显示、保存。层校验截获处模拟的是无驱动分支；真实驱动就绪时该函数的行为仍未验证。
- 本轮全部用例在实验堆、明确全局初值与受控内存中执行；真实程序的堆状态、链表头内容与驱动状态可能不同。`runtime_verified` 保持 `false`。
