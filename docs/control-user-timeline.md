# user门禁时间线：空闲计时被新事件续期，曾正常恢复ready

本轮只离线读取上一位图组的源码、338863行日志和两次原ControlStatus回执，没有启动控制服务、GUI、截图或输入。分析输入SHA-256为`33d82024495ef8f896a5b0bb085ec866864951188262b4358a77f1ccfb5f4712`；原日志摘要前后不变。脚本和结构化输出在本机`.local-analysis/control-user-timeline/analyze.py`及`summary.json`，不提交原材料。

原`_snapshot_locked`对user状态使用`max(0, max(last_user,last_physical_event)+10-now)`计算等待时间；`_tick_locked`在没有保持键/鼠标按下，且最后事件至少10秒前时转ready。`_handle`在ready/user状态处理key、point、raw时更新last_user。位图组控制线程正常存活、无emergency，窗口指示层未active，不能将这次恢复拒绝归入前一轮活跃绘制心跳超时。

原state-change证明服务曾三次ready：859113.7750873（启动）、859532.9198596、859829.7402528。后两次ready分别维持约3.8786和43.0507秒，之后在859536.798439/859872.7909749又转user。全组不是永久锁死。按处理事件间隙估算的quiet候选与这些转移一致，但日志代理的时间并非原生输入全部采集的证明，不能把candidate称为安全操作许可。

全日志处理记录point152815、raw29434、key120，共182369；另有2条其他类别input-processed，因此总input-processed182371。低层hook152935条，记录的injected均false；来源标记只能描述API提供的标志，不能确认操作者、设备、远程控制软件或来源进程。原采集没有坐标、按键值、设备/进程来源，不补推身份，不要求用户根据这些记录去停某个不明程序。

结论：本组两次门禁拒绝有直接的最近输入时间线支持，不能通过改state、清last_user/held集合、改变10秒条件或循环重启连接解决。位图计时加载成功但上传0，仍未现场验证。当前无需修改控制判定或计时模块；应优先安排一次明确的短时段，观察是否具备安静输入条件，再执行单组取证。不能把ready状态当作绕过原门禁的通行证。
