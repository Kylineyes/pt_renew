# 原菜单、宏与键盘分派的静态路径

本页接续 [运行对照记录](legacy-text-runtime.md)，记录 verification-31 的离线分析。已定位 `PT.EXE` 的菜单装载、菜单表绘制调用、选择器和宏分派，以及 `TRAXEDIT.OVR` 的 KEY 装载入口和 Information 分支。**这些是指令、文件内容和重定位相互核对的静态证据，没有证明此前 DOSBox 场景实际载入菜单或响应按键。** `runtime_verified` 仍为 `false`，产品仍为 0.9.0。

后续 [verification-35 现场验证](legacy-menu-live-verification.md) 已实际观察到启动页、主菜单、Information 和 Status，并取得 `C21.PCB` 工作文件名及文字计数；以下地址链仍属于静态证据。现场未验证宏展开或文字对象参数，四条 FT 参考走线与 `Tracks=0` 的差异继续保留。

## 菜单装载与解析

`1000:00aa` 从 `CS:0027` 的 Pascal 字符串 `TRAXEDIT` 初始化程序名。`1000:0109` 装入 `DI=0x35` 后显式 `PUSH CS`，引用的是 `CS:0035` 的长度前缀字符串 `.MNU`，而非仅因出现常量 `0x36` 就推断引用。构造文件名后调用 `324e:4393` 的查找包装；失败分支使用 `.MNU Not Found.` 和 `Program Aborted.` 提示，成功分支在 `1000:0179` 调用 `324e:2c31`。

`324e:2c31` 有打开文件、逐行读取和关闭文件的调用。其常量与隔离副本内容对应：

| 常驻 Pascal 字符串地址 | 内容 | 用途 |
| --- | --- | --- |
| `324e:2c16` | `*SECTION ` | 识别文件段开头 |
| `324e:2c20` | `MESSAGES` | 消息段 |
| `324e:2c2b` | `MENUS` | 菜单段 |
| `324e:2c29` | `\|` | 消息中截断分隔符 |

菜单段按文件顺序扫描 `#` 条目，读取后续标题和非空行；当前代码每个菜单最多收集 24 行。标题及菜单行中的 `$` 会替换为空格。解析器分配标题、行字符串和菜单结构，计数写入 `DS:70d0`，菜单远指针表基址为 `DS:69ea`，第一个菜单指针在 `DS:69ee`。消息计数和远指针表分别使用 `DS:70d2`、`DS:6dee`。

现有 MNU 的 MENUS 段包含 256 个 `#` 条目；按非空菜单的装载规则核对，`MAIN` 为第 1 项，`INFORMATION` 为第 88 项（`0x58`），`INFORMATION_STATUS` 为第 89 项。这是固定样本中的顺序关系，不是所有版本的协议常量。

## 绘制调用与菜单入口

| 地址 | 已核对的静态行为 |
| --- | --- |
| `324e:14ba` | 按菜单编号从 `DS:69ea` 表取结构，调用框体和标题绘制，再逐行调用 `324e:10ae` |
| `324e:10ae` | 从菜单行号和位置计算文字坐标，分派到文字绘制路径 |
| `324e:0fa4` | 逐字符调用 `324e:0f77`，横向步长为 7 |
| `324e:16bb` | 选择菜单项，使用输入队列，处理 Esc、Enter、首字母及方向选择，必要时调用 `324e:14ba` |
| `1000:0503` | 以菜单编号 1、宽度参数 0 调用选择器，再把结果传给主菜单分派 |
| `1000:054a` | 从主菜单项文本的首字符匹配输入，匹配后调用主菜单分派 |
| `1000:0420` | 将主菜单序号分派到对应功能；第 8 项对应 Information 覆盖入口 |

主循环 `1000:05c0` 中，`1000:0663` 在输入等于 `0x0d`（Enter）时调用 `1000:0503`。因此已有静态依据支持：**在主循环等待输入的状态，Enter 是主菜单选择入口，字母可以按菜单项首字符分派。** 这不等于此前启动页后的任意 Enter 都处于该状态。

选择器已有排队按键时可以直接返回匹配结果，未必先绘制菜单；不能把“没有截到菜单”直接等同于“菜单文件没载入”。Esc 分支在选择器中返回 0，但 verification-28 第二个 Esc 后 Windows 前景变化的原因仍未知。

这里只定位到菜单文字的绘制调用和布局步长，没有恢复菜单字符图案，也未把菜单字体与 PCB 对象字形混同。

## KEY 装载与宏展开

`1000:02a2` 引用 `CS:0091` 的 `.KEY`，构造文件名并查找。文件找到后，`1000:02cd` 调用覆盖入口 `1250:002a`；原始段为 `0250`。描述符槽位 2 映射到 OVR `0x1abab + 0x24e5 = 0x1d090`，这就是 KEY 装载函数。

块内常量 `0x24c9`、`0x24d6`、`0x24dc` 分别是 Pascal 字符串 `KEYMACROFILE`、`<DEF>`、`<ENDDEF>`。装载代码读取文件头，搜寻定义起点，读取宏名和触发键，并收集直到定义结束的按键行；单个宏最多收集 100 个按键，装载宏计数上限为 48。代码中的宏记录步长为 `0x72`，装载计数写 `DS:6932`，触发键位于 `DS:(记录号×0x72+4b21)`。

覆盖块内 `0x2512`、`0x251d` 的远调用经重定位表核对到常驻文件赋名和打开路径；它们不是单凭函数名猜测的读取行为。隔离 KEY 的 `LIST_COMPS` 定义仍是 `Alt+F10 → Esc, Esc, I, C`，其实际触发结果未观察。

| 常驻地址 | 已核对的静态行为 |
| --- | --- |
| `324e:0650` | 读取底层键码；扩展键先按扫描码加 `0x80`，再处理部分特殊转换 |
| `324e:0779` | 收集底层输入，写入字符队列；也会把特定指针按钮状态转为 Enter/Esc |
| `324e:08a4` | 写入 `DS:60e8` 起的队列，读写索引在 `DS:6930` / `DS:692e`，代码处理 0 至 2000 的循环索引 |
| `324e:0a30` | 等待非零队列字符，在相关开关允许时匹配已载入宏表 |
| `324e:0965` | 展开宏记录中的按键；遇到其他宏触发键会递归展开，否则重新入队，递归计数检查小于 10 |
| `2964:36cc` | 编辑器输入入口之一，调用取键路径，再处理部分导航和命令 |

宏允许开关 `DS:68b9` 在启动初始化路径中显式设为 1；文字询问等路径会临时关闭它。宏开关的当前值、录制状态、底层键盘环境和当前命令状态都会影响响应。静态找到装载与展开代码并不证明此前场景中 `.KEY` 已成功读入，详见 [独立静态复核](legacy-menu-static-validation.md)。

## Information 与可观察的文件名

MNU 的主菜单第 8 项为 Information，分派目标对应覆盖描述符 `107c:0025`，映射到 OVR `0x29c5` 块内 `0x1b83`。该函数压入 `0x58` 和 0，再调用菜单选择器。远调用重定位目标为原始 `224e:16bb`，与常驻选择器吻合。

选择结果 1、2、7 分别到块内 `0x11f1`、`0x031b`、`0x0c99`，与 MNU 的 Board Dimensions、Components、Status 顺序吻合。Status 代码填充 15 行内容，并使用 `0x59` 对应状态菜单；工作文件名缓冲区 `DS:c8fc` 先经常驻 `324e:0000` 分解路径，只组合名称与扩展名，再写入 `DS:cd2a` 的第 11 行显示值。MNU 同一行是 `Work File Name`，因此该路径可作为后续实际文件名观察的目标，但不能单独证明完整路径或成功读取内容。状态行显示值最多取 24 个字符。

Status 使用专用选择器 `324e:1a6b`。该选择器按 Esc 返回 0 时跳过报告输出；非零选择会进入 `SAVE FILE NAME` 询问，只有询问返回非 Esc 才打开输出。后续运行应先记录状态页，再单独按一次 Esc 并截图核对返回；不要连续确认。下次运行应在新场景中逐步核对：启动页、主循环画面、菜单、Information、Status 的文件名和计数；每步都先查控制状态并截图。菜单出现或状态显示一个名字仍不足以完成文字对象属性和字形对照。具体参数、重定位和退出条件见 [独立静态复核](legacy-menu-static-validation.md)。

## 可复核工具

新增 [InspectLegacyMenu.java](../tools/ghidra/InspectLegacyMenu.java) 是本项目编写的只读 Ghidra 导出脚本，不包含原程序反编译结果或原始字节。它绑定上述 EXE 摘要、语言和地址基准，导出 18 个指定常驻函数的已有定义、引用、指令及反编译结果，始终标记 `runtime_verified=false`。函数缺失和反编译失败分别记录；不会自动创建函数或修改分析数据库。

对已经完成分析且按 `0x1000` 基段装载的本地项目执行，路径按本机实际位置替换：

```powershell
& 'C:/工具/ghidra/support/analyzeHeadless.bat' `
  'C:/临时研究项目' TextResearch `
  -process PT.EXE -noanalysis -readOnly `
  -scriptPath 'C:/仓库/tools/ghidra' `
  -postScript InspectLegacyMenu.java `
  'C:/仓库/.local-analysis/新的场景/resident-review.json'
```

输出必须是新的绝对路径，脚本拒绝覆盖现有文件。结果含原程序反编译材料，仅保存在忽略的本地研究目录，不提交或重新分发。工具仅覆盖常驻锚点；本轮覆盖块分析还需配合既有覆盖映射工具及本地定向导出。

本轮使用 Ghidra 12.1.4 对现有数据库以 `-noanalysis -readOnly` 执行脚本，18 个目标函数均存在且反编译完成；重复指定已有输出路径时，脚本按预期拒绝覆盖。既有覆盖映射工具的 16 项单元测试全部通过，并另行核对菜单顺序、状态页文件名行和隔离输入摘要。这些检查不消除 16 位反编译中参数、段值及条件标志的歧义。覆盖块按原样副本临时导入，分析后不保留导入数据库。完整本地证据、交叉核对脚本和运行日志位于 `.local-analysis/verification-31/`。

## 桌面核验边界

verification-32 使用全新目录和单个 Windows-MCP 连接，仅查询控制状态并请求截图。状态为 `ready`、generation 1；截图成功且可见 Orca 桌面窗口，但元数据报告 `No active window found`、`No windows found`。当轮因无法交叉核对焦点而停止，没有启动 DOSBox、没有挂载原安装或隔离输入、没有发送键鼠输入；连接随后正常结束。

后续独立诊断核对 Windows-MCP 0.8.8 的 `desktop/service.py`：`use_ui_tree=false` 路径明确跳过窗口枚举，主动返回空窗口列表和空活动窗口。因此 verification-29/32 的上述空值是未采集窗口数据，不能据此认定焦点异常；历史停止动作保留为当时的核验边界。启用 UI 树快照或配合只读 Win32 HWND/PID 观测才能补足焦点核对。

运行时尚未确认实际载入文件名、菜单响应或文字对象参数，也未解释 verification-28 的窗口变化。未修改 Qt、PCB 字形、方向/缩放、铜层判定或发布包；本轮未运行 Qt 构建或 CTest，已运行研究脚本、覆盖映射单元测试、输入摘要及文档检查。
