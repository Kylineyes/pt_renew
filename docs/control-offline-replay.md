# 健康日志离线重放：多阶段累计覆盖心跳停更区间

本轮仅读取代码与上一轮日志，未启动GUI、控制服务、钩子、截图或键鼠。新增[离线重放工具](../tools/replay_control_health.py)及[8项测试](../tests/test_control_health_replay.py)，将3条过期采样按相同旧心跳归并为两段停更区间，按阶段起止时间的并集计算覆盖，嵌套/重叠阶段不重复计时。它只接受正常关闭且丢失数0的单次日志，拒绝矛盾判定、损坏时间和拼接日志；输出采用新文件，不能覆盖输入。

静态代码可解释这种累计模式：原`_Indicator._run`等待后依次执行显示器枚举、各图层透明度更新、显示/光标/消息泵，最后才更新heartbeat及applied。原`_Layer.set_opacity`在透明度变化时调用`flash_overlay._push_bitmap`；后者每次获取DC、建立兼容DC/DIB、复制BGRA、调用UpdateLayeredWindow，最后恢复选择并释放位图/DC。多次调用的墙钟耗时可以累积超过1秒，即使单次都小于1秒。这只证明源码路径和本组调用区间一致，不证明分配、像素复制、系统API或调度中哪一项慢。

全日志有110201条hook-event和130743条input-processed，但两段停更区间内均没有这些记录；首次hook-event在853586.10165，晚于第一次看门狗fail-open 853268.482442。不能用全场输入事件数量证明第一次超时由高频输入日志直接造成，也不能据两段局部无事件排除进程内其他线程、日志写入、未记录的系统活动或全局负载。来源标记不构成用户操作归因。

下一步的最小取证范围应先细分位图上传中的DC/DIB准备、BGRA复制、UpdateLayeredWindow及资源清理耗时，记录大小/调用次数，同时保留每轮完整进度；再决定是否值得做图层资源复用或其他性能修复。当前已准备`tools/control_bitmap_timing.py`及[待许可的30分钟现场方案](control-bitmap-timing-plan.md)。新模块只替换flash模块自己持有的API引用，底层共享对象不改；在指示层线程的`_push_bitmap`范围内汇总各API调用耗时，每次上传一条事件，异常继续传播、清理仍执行。启动器默认不加载，只有明确`indicator_bitmap_timing=true`、同时批准健康采样并冻结模块摘要才可启用。5项假API测试覆盖参数/返回值、异常与清理、其他线程不记录、缺入口拒绝及重复安装；位图计时模块在用户本次30分钟许可下已于新隔离进程加载，installed事件正确，但唯一组在前景检查和原门禁恢复处受阻，实际上传0，现场计时功能仍未验证。控制链约14分6秒正常结束；详见[本轮结果](control-bitmap-timing.md)，没有续开连接。当前没有缓存/绘制功能改动，不能在一轮中途续写心跳掩盖未完成显示，不能放宽1秒阈值或跳过故障拒绝。
