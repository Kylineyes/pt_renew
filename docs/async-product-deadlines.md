# 原阶段剩余时限、创建者运行器与失败收尾

从已核对的 `dev=origin/dev=afb22b787c5faa4693430eaf6114386d6d24b9dc` 建立独立分支 `feat/async-product-deadlines`。本阶段继续[统一交接](agent-handoff-20261030.md)指定顺序：先补剩余 deadline，再接实际原 Popen 报告交换和各阶段失败收尾。所有生产入口默认禁用，`ready_for_live=false`、`max_product_launches=0`。没有启动真实控制服务、产品、COM/UIA、输入钩子、桌面请求或新的图片任务。

## 时限从原输入前起算

`Ledger` 在铜分析按钮或 NET 文件框“打开”按钮的原输入之前，唯一保存 `gate_trigger_ns`。随后路由、attach、Snapshot、实际 read/ack 核验、普通输入和探针都使用同一阶段截止。独立 `RaceClient` 的离线接口在首次门闩图请求中绑定调用方保存的原起点；已由产品输入绑定的起点必须完全相同，不能重新计时。

| 阶段 | 严格截止 | 推进条件 |
| --- | --- | --- |
| 门闩图 | 原起点 +20秒 | 当前图实际 read/ack、应用后验及本地完成记录均成功 |
| 编辑与编辑图 | 原起点 +50秒 | 真实选择/Delete、编辑图实际 read/ack及应用后验完成 |
| 开始 release | 原起点 +55秒 | 唯一机会、原应用仍等待、应用时钟余量大于5秒 |
| release 完成 | 原起点 +60秒 | 原 gate-released、回执、句柄清理和完成记录均返回 |

`McpProductTransport` 在 schema/文件凭据/截图协议预检前取单次绝对截止，调用前再用剩余时间设置 `asyncio.wait_for`。原35秒工具上限保持；阶段只有13秒时只分配13秒。原始回执、PNG、规范回执和最后 end 文件的落盘均在截止内检查。实际服务管道回执的原字节和摘要也计时。

`BoundedUiaProbe` 在产品身份/解释器/77文件包/全部模块摘要预检之前取截止，单次不超过原5秒且不晚于阶段/原总截止。request、原Popen创建前审计、结果身份校验、最终源码复核及接收记录落盘全部计时。迟到结果不置 `accepted=true`。同一次发现/批量观察仍共享32次计数，正常完整 NET/铜仍是含发现31/22次。

release 在消费机会及写入尝试记录后检查55秒门槛；实际 `SetEvent` 前再次按应用和本地原截止核验，避免慢日志使信号在余量不足时发出。SetEvent 返回本身仍不构成有效释放。

这些是拒绝条件及合作式异步等待约束。同步哈希/文件系统调用可能阻塞，在途 COM 或服务动作也不会因父 `wait_for` 到期立即停止。因此本阶段没有获得真实动作时限或未来耗时上界，不能据此改为 live-ready。

## 实际创建者与原服务管道

`runtime.py` 和 `runtime_worker.py` 直接创建并保存原 Popen，在身份核验之前保存对象和账本。子进程先等待父绑定，父取得创建时原句柄/PID/birth/image 后发布同上下文绑定，子再核对自身 PID/birth 和冻结解释器，才执行新冻结入口。绑定、报告及摘要回执使用完整文件原子发布，拒绝覆盖。不存在额外短命握手进程。

`CreatorRuntime` 将 supervisor/client/service 的报告逐层绑定到各创建者自己的原对象。子报告只有在本父原 Popen 退出0后才可验收，最外层仍由 `RootWitness` 在根原对象存活时绑定并于退出后结算。身份未知、非0、缺报告、错摘要及已发现却缺原创建对象的子孙都保留缺口。后来打开的查询句柄和报告 JSON 不能补作创建来源。

`OriginalMcpConnection` 使用该客户端已经持有的服务原 Popen 的 stdin/stdout，执行 MCP initialize/tools/list/tools/call，保存原管道回执，再通过现有 MCP SDK 转回原 `model_dump` 格式。它不调用另行创建服务的 `stdio_client`，也不自动重连或重试。服务 EOF 之后仍等待同一个原 Popen，并验收服务自己的创建者报告。

`ProductBootstrap` 在同一客户端装配原产品创建器、一次主窗发现、共享32次的批量探针、MCP传输、实际read关口、原应用日志和 `ProductSession`。各组件创建后立即保留，后续初始化失败也可由收尾器访问。板图使用调用方冻结摘要，A/B副本继续逐次核验。

`service_driver.py` 是实际服务的冻结入口适配，仍调用原 `run_control_diagnostics.serve` 核验77文件包、当前上下文/批准及原600/900预算，保留原门禁、指示层和可选包装。它尚未现场运行。服务解释器/虚拟环境、完整依赖加载、真实Windows服务和产品冷成本均需兼容性验证；无GUI原Popen测试不能替代这些证据。

本阶段实际无GUI测试构造了 supervisor→client→service，客户端另直接创建一个只等待stdin EOF的标准库子进程模拟 product 角色；四个身份及其原退出0、三层报告和根见证都通过。测试服务只处理合成 JSON-RPC，不导入控制包，也没有运行 PT 产品。

## 失败后按原阶段正常收尾

`ProductSession` 创建时即具备关闭组件，不再依赖成功 attach 门闩。门闩前依据原应用全部 request/worker-returned/callback 终态判断是否可正常关闭；在途工作或未知日志继续拒绝。失败组的门闩必须原 aborted→worker-returned→callback-discarded，不能补成有效 release。

文件框失败收尾有单独 `cleanup_only` 模式：120秒到期后新截图→指定会话实际read/ack→唯一明确“取消”→普通主窗后验，然后才正常 Alt+F4。该模式不能 Type 或打开文件。即使打开按钮点击已发出而后验失败、文件框对象尚未创建，也保存原点击尝试并允许进入新读图取消流程；不会重发打开。

`ShutdownCoordinator` 在任何初始化阶段保留 owner/creator/probe/registry/session/connection。冷却期间只发布本地 stop 标记、poll 原对象和保存审计；它不自动发送桌面动作。主窗未绑定、创建身份未知或探针 unknown/failed 时明确保留对象，不能宣称正常退出已经完成。迟到exit0只补生命周期，不清首次失败、token、120秒或原截止。

产品及所有已知探针正常退出后，上层才可显式关闭原服务stdin并等待/验收报告。35/5/40秒退出余量、600/900秒总预算不扩大。创建者驱动异常结束时若仍有原子进程，运行器保留原对象，仅做本地退出观察；已知产品/探针/下层创建者退出后可向直接持有的服务发送一次正常EOF。若900秒后仍未知，保存 deadline-unknown，继续被动持有原对象，不再发送控制请求，不将这段被动生命周期等待计作900秒内成功。它可能需要后续人工处理真实卡住的进程，不能宣称所有异常都可保证exit0。
